# Публикация проекта

## Публичная страница

Основной пользовательский интерфейс:

- `https://sankhipkate.github.io/countrymatcher/`

Отдельный лендинг:

- `https://sankhipkate.github.io/countrymatcher/landing/`

Папка `/matcher/` содержит CSS и JavaScript приложения, но не имеет собственной пользовательской HTML-страницы или перенаправления. Прежний `/pilot/` не получает нового публичного адреса.

## Источник публикации

GitHub Pages workflow собирает из `countrymatcher/` allowlisted Pages artifact и публикует его как корень сайта после успешного выполнения тестов.

Рабочий процесс:

1. изменения вносятся в отдельной ветке;
2. запускаются автоматические тесты;
3. создаётся pull request в `main`;
4. после merge GitHub Pages собирает и публикует allowlisted artifact из `countrymatcher/`;
5. проверяются корневой адрес, `/landing/` и отсутствие пользовательской страницы по `/matcher/`.

## Текущая версия

Единственный технический источник текущего номера продукта — файл `VERSION`. Номер подставляется в пользовательский footer только при сборке Pages artifact и не дублируется в runtime-коде, `package.json`, `package-lock.json` или cache keys.

В пользовательский RP4 matcher подключены:

- Испания;
- Аргентина;
- Уругвай;
- Бразилия;
- Португалия;
- Мексика;
- Парагвай;
- Колумбия;
- Черногория;
- Чили.

Текущий production использует бесплатную анкету, одну полностью открытую подходящую или условно подходящую страну до оплаты, платный полный результат и отдельный Quality of Life editorial layer после налогов.

Runtime JS/CSS и динамические data URL используют отдельный deployment-scoped `BUILD_ID`, а не номер продукта. Для GitHub Pages `BUILD_ID` формируется из commit SHA, `GITHUB_RUN_ID` и `GITHUB_RUN_ATTEMPT`, поэтому повторный deployment того же commit получает новый cache key. Это важно для `fx-fallback.json`, который может обновляться уже после основной сборки artifact. Один `BUILD_ID` намеренно инвалидирует весь runtime asset/data graph при каждом deployment; для текущего размера проекта это принятый компромисс в пользу простой и надёжной согласованности. Переход на per-file content hash потребует сначала обновлять изменяемые deployment-time данные, включая FX fallback, и только затем рассчитывать хеши и инъецировать ссылки.

Актуальный состав пользовательского интерфейса описан в `README.md`; нормативные правила исследования и расчёта находятся только в `../source-documents/canon-v4.0/COUNTRY_RESEARCH_STANDARD.md` и `../source-documents/canon-v4.0/MATCHING_AND_RESULT_STANDARD.md`. Текущий активный контракт — `data/research-package-v4.0.schema.json`; файлы Research Package 3.0 сохраняются только как архивные инертные материалы.

## Нормативные правила версионирования

`DEPLOYMENT.md` — единственный нормативный документ по присвоению и публикации версии приложения. Техническим источником текущего номера служит только файл `VERSION`.

Версия имеет формат `COUNTRIES.FEATURES.FIXES`:

- `COUNTRIES` — количество стран, подключённых к пользовательскому расчёту;
- `FEATURES` — номер крупного изменения анкеты, движка, структуры результата или пользовательских возможностей без добавления страны;
- `FIXES` — номер опубликованного набора исправлений и небольших изменений.

Правила увеличения:

- добавление страны увеличивает `COUNTRIES` и обнуляет следующие компоненты;
- крупное изменение функции увеличивает `FEATURES` и обнуляет `FIXES`;
- опубликованные исправления без крупного изменения функции увеличивают `FIXES`;
- изменение исследовательских данных, меняющее пользовательский результат, увеличивает `FIXES`;
- изменение внутренних материалов, не меняющее приложение или пользовательский результат, не требует новой версии;
- deployment-only обновление volatile artifact data, например свежего FX fallback без изменения продукта, не требует новой product version и получает новый `BUILD_ID`.

После публикации номер product release считается использованным навсегда. Два разных product release не могут иметь одинаковую версию. Номер изменяется до commit и push, когда изменение по этим правилам требует нового product release.

Ручная синхронизация номера между файлами запрещена. При сборке:

- `APP_VERSION` берётся из environment, а при его отсутствии — из `VERSION`;
- `BUILD_ID` берётся из environment, в GitHub Actions формируется из deployment identity, а локально имеет безопасный fallback;
- footer получает `APP_VERSION`;
- статические относительные JS/CSS runtime references получают `BUILD_ID`;
- динамические RP4 JSON, profile schema, Quality of Life JSON и `fx-fallback.json` получают тот же `BUILD_ID` через runtime helper.

Тесты проверяют source tree и собранный artifact отдельно: source не содержит вручную прошитых release cache keys, а artifact должен использовать единый deployment `BUILD_ID` для runtime asset/data graph.

## Проверка перед merge

Единственный канонический release gate запускается из корня репозитория:

```bash
bash ./verify
```

Корневой `verify` является только переносимой обёрткой и определяет корень относительно собственного расположения, а не текущего каталога или наличия `.git`. Вся логика проверки находится в `countrymatcher/scripts/verify-project.sh`. Поэтому тот же gate работает в обычном clone/worktree и в распакованном архиве без Git metadata; без `.git` пропускаются только Git-specific checks.

Verifier сначала выполняет дешёвые проверки структуры и syntax, затем Git checks при доступной metadata, после чего подготавливает Node dependencies через чистый `npm ci`, создаёт/обновляет локальное изолированное Python-окружение `.verify-venv` по `requirements.txt`, валидирует все активные RP4-пакеты, запускает полный `npm test` и проверяет синтаксис JavaScript. В Git worktree проверяются unstaged, staged и последний committed diff. GitHub CI и Pages обязаны вызывать этот же root verifier вместо собственной дублирующей последовательности.

`npm test` имеет dependency bootstrap и при отсутствующем или рассинхронизированном `node_modules` сначала выполняет `npm ci`. Прямой `node --test` не используется как release gate, потому что он обходит npm lifecycle и dependency bootstrap.

README и этот документ обновляются вместе с изменениями публичных адресов, правил публикации, пользовательского поведения или канонического release gate. Текущий номер продукта меняется только в `VERSION`.
